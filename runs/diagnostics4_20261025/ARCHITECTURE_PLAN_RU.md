# FlyGraph 100M: что применять из Kimi, Qwen и MiniCPM

Аудит выполнен по реально загруженным EXT2/EXT3 и копии `src/model.py`; численные результаты — `metrics/architecture_audit.json`. Это план следующего исследования и отдельная инженерная проверка. Новая архитектура не обучена, результат сравнения с Qwen/MiniCPM отсутствует. Изучение документации не снимает403 при загрузке эталонных весов.

**Точная текущая модель.** 100,028,328 параметров,14 блоков `dadadadadadada`, width768, FFN2048,12 query-heads,4 KV-heads, delta key32/value64, context2048. Embedding/output tied, vocab8192. FFN66,060,288 параметров, delta-mix16,644,264, attention-mix11,010,048, embedding6,291,456; остальное нормы. Pre-RMSNorm eps1e-6, RoPE theta10000, SwiGLU. Attention Q/K не имеют QK-RMSNorm; L2-нормирование Q/K в delta — другая операция. Нет MoE, retrieval, MTP и свёртки в delta.

Delta хранит FP32 state12×32×64 на блок. Семь блоков дают672KiB на последовательность. Семь GQA-блоков при2048 токенах требуют ещё14MiB BF16 K/V, без активаций, logits и временно повторённых KV. Состояние конечно только у delta; память всей модели не константна. При нескольких токенах текущий `delta_rule` строит T×T decay/Gram-матрицы и решает треугольную систему. Это квадратичная реализация prefill/training, хотя decode одного токена рекуррентен.

Токенизатор — частотные целые лексические фрагменты с UTF-8 byte fallback, не BPE. На96 новых dev-записях исходные вопрос+варианты восстанавливаются точно, но доля fallback-токенов79–84%. Это измерение английских задач, не доказательство качества русского. Улучшать только формат ответа недостаточно; фактические readout/численные проверки представлены отдельно в отчёте диагностики.

**Что реально добавлено сейчас.** `src/chunked_delta.py` — самостоятельная обёртка вокруг прежнего delta_rule с размером блока64 и переносом FP32-state. Она уменьшает размер временных delta-матриц до64×64 на блок (общий объём операций delta линейнее по длине при фиксированном размере блока); full attention остаётся прежним. Это не импорт KDA и не новая обученная архитектура. Проверка `src/verify_chunked_delta.py` сохраняет результат в `metrics/chunked_delta_verification.json`; только статус `passed` там означает успешную численную проверку. Побитовое совпадение native resume после смены порядка операций не обещается; опубликованные EXT3 training code и weights не изменены.

**Места расширения в коде.** `Config` и `Model.__init__` должны получить явный список типов блоков перед экспериментами3:1. `Model.forward` сейчас берёт длину прошлого из `cache[1][0].shape[2]`: при перестановке слоёв это предположение сломается; нужен cache-position, независимый от типа блока. `Attention.forward` — место для сравнения GQA без `repeat_interleave` и optional QK-Norm. `Delta.forward` — место изменения gates; это уже новая обучаемая функция. `Block.forward` — zero-init residual-adapter/LoRA с проверкой совпадения исходной функции. `Tokenizer.encode` и tied `embed.weight` — согласованная миграция словаря; менять только tokenizer.json нельзя.

Нулевые residual-adapters или добавленные блоки с нулевым выходом могут сохранить исходную функцию и служить warm-start, но требуют обучения. Замена width/heads/key-dim/deep-thin формы делает большинство тензоров несовместимыми; требуется новый pretraining или явное преобразование/дистилляция. Новый BPE допускает перенос совпадающих токенов и адаптацию embeddings; это существенное continued pretraining, не точное возобновление. RoPE scaling сохраняет размеры, но требует обучения и отдельной long-context оценки. Большой MoE не решает наблюдаемую проблему данных и не запланирован.

**Параметры и compute100–300M.** Только подсчёт на meta-device, без выделения весов и без запуска200/300M: текущий100,028,328; те же width/FFN с28 слоями193,764,432 и42 слоями287,500,536. Один переход с8192 на32768 vocab при width768 добавляет18,874,368 параметров, всего118,902,696. Гипотетический30×576 hybrid с32k vocab —131,869,134. Это варианты геометрии, не обученные модели. Словарь151,669 при width768 занял бы116,481,792 параметра только в tied embedding и уже превысил весь целевой100M бюджет.

Для грубой планировки, **не гарантии качества**, рассмотрим2B/4B/6B токенов для100M/200M/300M. По плотной оценке6ND это1.2/4.8/10.8×10^18FLOPs без дополнительных расходов attention, optimizer и data pipeline. [Chinchilla](https://arxiv.org/abs/2203.15556) мотивирует совместное масштабирование данных/параметров; эти конкретные budgets — наш сценарий планирования, не обещание превосходства. Современный маленький полезный LM часто обучают намного дольше: приведённый SmolLM2 пример имеет2T, а не2B токенов.

Реальный EXT2:2,899,624 входных токенов за9329.91s всего run, около311tokens/s на4CPU; supervised targets1,045,986. При этой грубой end-to-end скорости2B токенов заняли бы около74.5 суток. Экстраполяция на сотни миллионов параметров без измерения ненадёжна. В этой среде GPU нет; скорость/часы на GPU не измерены, аренда не выполнялась. Известная история коротких EXT-прогонов не заменяет многомиллиардный корпус, а полный исторический pretraining lineage до доступных checkpoint неизвестен.

**Следующий проверяемый приоритет.** После диагностики зафиксировать новую внешнюю dev/test-схему и набор опубликованных семантических данных с точной лицензией/revision; текущие раскрытые test не использовать для выбора. При сохранённой модели сравнить один control с одним изменением: supervised текст ответа и короткие готовые объяснения вместо доминирования letter-only обучения, с сохранением языковой смеси. Уравнять input/supervised-token budgets, order/seed и время; заранее определить dev-критерий и независимые языковые/QA/перестановочные проверки. Для короткого CPU-пилота1M входных токенов — около54мин по измерению EXT2, плюс отдельный запас на checkpoint/eval; это оценка feasibility, не обещание качества. Только после подтверждённого эффекта данных — WSD либо Muon, по одному изменению. Перед большим новым backbone нужны доступный compute, корпус и контрольный baseline. Никаких самодельных benchmark-ответов или платных teacher API.

Источники проверены2026-10-25. Репозиторий `QwenLM/Qwen3.5` сейчас перенаправляется в `Qwen3.8`; название нового репозитория не использовано как подмена baseline. [MiniCPM-V официальный README](https://github.com/OpenBMB/MiniCPM-V) перечисляет4.7-1B; результаты карточки не включены в наши измерения. Отсутствие скачанных точных Qwen3.5-0.8B и MiniCPM-V-4.7-1B остаётся блокером фактического сравнения.
